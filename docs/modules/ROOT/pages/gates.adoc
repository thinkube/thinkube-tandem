= The two gates
:page-type: concept

== Gate 1 — Sign

Signing freezes a cut into a TEP. The gate refuses:

* an empty cut;
* a change with no acceptance criteria ("nothing proves this");
* a change with no grounding (no place in the code);
* an ask in the cut with an undecided question;
* a cut that neither lands documentation nor carries a recorded
  exemption — documentation is required for every cut at signing, and
  the only way past it is an exemption with a reason.

The click mints `TEP-<you>-<n>` and a machine-local HMAC token bound to
the pair you actually saw: the rendered cut screen plus the grounded
content underneath it — the documentation decision included. There is
no expiry — instead, any edit to the signed content makes the token stop
matching, and dispatch refuses until you sign again. What runs is exactly
what you approved, enforced cryptographically rather than by convention.

== Gate 2 — Accept

A delivery page opens by naming the run that produced it and when — or
says plainly that the run was never recorded, for an old delivery that
predates the field — before any other section. It then lists every
proof: one per acceptance criterion, executed by the real closing gate,
plus the repository's own test suite. Accepting:

* is refused for a delivery that was withheld, or one with no proof at
  all;
* is refused while any acceptance criterion of the cut is red — an
  unkept promise is the one thing that is never handed over;
* is refused while a declared documentation obligation is unmet (the
  docs gate blocks by default; `thinkubeTandem.docsGateMode: advisory`
  is the recorded escape hatch for a documentation obligation that
  slipped through to a delivery — documentation itself is already
  required at signing, with a recorded exemption as the only way past
  it there);
* runs in the canonical order merge → stamp → retire: a refused merge
  aborts before anything is stamped; worktree cleanup is best-effort and
  never fails a landed accept.

Everything that did NOT arrive is printed on the page — UNDELIVERED
items, confessions found by the honesty scan, unmet obligations. Red is
shown as red; there is no override on a red promise.

== Findings — what the machine could not settle

Not every red thing is a veto. A delivery also carries *findings*: things
the machine noticed, could not settle, and has no actor left to route to
— a standing test that stayed red after every repairer was spent, a
review that disagreed, a size or reachability opinion, production code
that imitates the editor platform.

These get their own section on the delivery page and they do **not**
block Accept. That is deliberate. A rule may veto only when its failure
names somebody who can still act; by the time you are reading the page,
that somebody is you. Holding four kept promises hostage to a hygiene
opinion nobody can act on serves nobody — so the machine says what it
saw, in full, and the judgement is yours.

Two things still veto, and only two: an unkept promise, and a product
that does not build. The second is not a matter of taste — handing over
something that cannot ship harms whoever pulls it, whatever you decide.

== Observations — what only the running product can show

Some acceptance criteria cannot be driven by any check: they are about
what the product *looks like* or *feels like* when it runs. These are
recorded as observations rather than graded green, listed on the
delivery, and left for you to confirm by using the thing. The machine
never marks an observation proven on its own account.
